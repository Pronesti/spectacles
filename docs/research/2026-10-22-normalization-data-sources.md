# Sources for live-event normalization and Attendance creation

Research date: 2026-10-22. Geographic priority: Argentina and Latin America, with worldwide alternatives.

This is source research and recommendations, not an implementation plan or an amendment to the approved [database design](../superpowers/specs/2026-10-22-live-events-database-design.md). No integrations, accounts, paid subscriptions, migrations, or product code were created.

## Findings and recommendation

Use several sources with distinct responsibilities. An API that can display information does not necessarily permit keeping an editable copy in Spectacles indefinitely.

1. **Artists and underlying songs:** shortlist MusicBrainz for matching and durable core metadata; use Wikidata for additional identities and cross-references. Their identifiers fit the approved internal-ID-plus-provider-reference model.
2. **Venues:** evaluate Geoapify first for a hosted lookup whose published terms explicitly permit storing results. Compare its regional coverage with Google Places before choosing. Overture Places and Foursquare Open Source Places are alternatives for building a durable search index; they are not turnkey application autocomplete.
3. **Argentine historical concerts and setlists:** setlist.fm has directly observed relevant records and the best documented fit among the reviewed sources for this combination. However, its standard terms do not establish permission for our persistent, editable imports. Obtain a suitable agreement before adopting it for that purpose. MusicBrainz Event setlists are a technically usable open-data alternative with unproven regional completeness.
4. **Future event selection:** evaluate regional publisher feeds or agreements first. Ticketmaster has a documented discovery API, but Argentina coverage was not verified. JamBase is a paid event/history candidate whose documentation supports local ingestion; regional coverage and contractual retention rights still need verification.
5. **Tours:** use MusicBrainz Series of type Tour and Wikidata when a matching entity exists. Otherwise accept a tour name from an appropriately licensed source or leave the relationship empty. No reviewed source establishes comprehensive named-tour coverage for Argentina.
6. **Playable song references:** Spotify or Apple Music can supply catalog links, subject to access and use rules. They should not define the underlying Song identity.

Do not make general website scraping a prerequisite for Attendance creation. Many sources already provide APIs or datasets; several restrict scraping, and regional sources without verified APIs would need a feed/agreement or site-specific extraction permission.

## What was verified

Reviewed official provider documentation, official terms, developer portals, open-data documentation, and selected provider records. This establishes documented schemas, access paths, and stated restrictions. It is not a benchmark of API results, availability, latency, or regional completeness.

- No credentialed catalog or event API calls were made. No provider signup, key application, purchase, or contact message was sent.
- Provider websites and publicly indexed documentation were read. Some live pages failed or rendered only a JavaScript shell; these limitations are identified below.
- Two additional read-only HTML checks fetched the TuEntrada homepage and the specific Passline event page listed below. Both returned HTTP 200, with no `application/ld+json` script blocks found in their initial HTML responses. These checks did not execute JavaScript or test every event page or microdata format.
- Source excerpts and example records demonstrate presence, not an accuracy rate or permission to import their content.
- Recommendations about architectural fit are inferences from the documented capabilities and the approved Spectacles requirements.
- Prices and access policies are dated findings, not a provider quote or a promise of future access.

### MusicBrainz: useful across all six requested domains

The database overview classifies artist, Event, Place, recording, Series, work, relationship, and URL data as core. Annotations, tags, ratings, search indexes, and other supplementary data have different licensing. Core CC0 data can support durable normalization without treating all API-returned fields as equally reusable. The hosted API is separately rate-limited to one request per second per client application, requires an identifying User-Agent, and directs commercial users to a plan/contact. [Field classification](https://musicbrainz.org/doc/MusicBrainz_Database), [licenses](https://musicbrainz.org/doc/About/Data_License), [service conditions](https://musicbrainz.org/doc/MusicBrainz_API/FAQ)

An Event can include a textual setlist; its syntax distinguishes artists, songs/works, and notes and can embed MBIDs. Convert that representation to relational entries rather than storing it as Spectacles' canonical list. A Series of type Tour supplies a real tour identifier; a Place supplies a venue identity with address/coordinates where available. [Setlist syntax](https://musicbrainz.org/doc/Event/Setlist), [API examples](https://musicbrainz.org/doc/MusicBrainz_API/Examples), [Series](https://musicbrainz.org/doc/Series), [Place](https://musicbrainz.org/doc/Place)

Regional searches found relevant artist/work/recording data, but did not establish a MusicBrainz Tour entity for every searched Argentine tour. A live album or compilation sharing a tour's name is not evidence of a Tour entity or a complete show setlist.

### setlist.fm: payload fit versus durable use

The published terms permit only short caching under the standard license, require attribution and as-is presentation, and restrict modification and competing services. These conditions conflict with assuming a permanent collaborative copy is permitted. A manual click, one-time import, private visibility, or user confirmation does not itself establish broader rights. Treat suitable licensing as a prerequisite, not scraping as an alternative. This is a material integration limitation absent from the original database discussion. [Terms](https://www.setlist.fm/help/terms)

The documented song object contains a title, guest (`with`), original artist (`cover`), notes, and a tape flag; it does not supply a composition ID. The main artist plus guests describe performers; the original artist of a cover must not be imported as an onstage performer. A tape entry also must not silently be counted as a live rendition. A tour supplies a name, not a tour ID. [Song schema](https://api.setlist.fm/docs/1.0/json_Song.html), [tour schema](https://api.setlist.fm/docs/1.0/json_Tour.html)

Each source setlist is artist-specific. Combining several artists into the approved single Attendance list requires deliberate ordering; source IDs alone do not establish that order. Flattening an encore into a note fits the current design, while richer tape/medley semantics would need a later explicit decision. Research does not add those fields automatically. [Setlist schema](https://api.setlist.fm/docs/1.0/json_Setlist.html)

### JamBase: promising paid Event aggregation, with limits

Its documentation describes keyword search, cross-provider lookup, local ingestion, and historical access by entitlement. Those are unusually relevant capabilities for reducing entry across several upstream catalogs. A contractual fit and a representative Argentina/Latin America sample remain necessary. [Search](https://data.jambase.com/api/docs/search), [reverse IDs and data](https://data.jambase.com/data), [bulk ingestion](https://data.jambase.com/api/docs/bulk-ingest)

The indexed official pricing comparison lists a noncommercial developer tier with 1,000 monthly calls and paid overage, Pro with three years of artist/venue history, and Pro+ with full history. It lists monthly prices of USD 1,800/3,000 for Pro/Pro+, or annual-billing equivalents of USD 1,500/2,500 per month. The live pricing page rendered blank to the research tool, so these are indexed published figures that need a current quote, not independently tested checkout prices. [Pricing](https://data.jambase.com/products/)

### Spotify's current access boundary

The October 2026 quota documentation requires a Premium app owner for Development Mode and limits it to five authenticated Spotify accounts. Its extended-quota application criteria include an organization, a launched service, and at least 250,000 monthly active users. Those rules make unrestricted production access a dependency to verify rather than assume. [Quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)

The five-account rule is not automatically a five-user limit on Spectacles: Client Credentials is a server-to-server flow without user authorization. Catalog search through that flow is plausible from the docs, but was not tested for a newly created app. Account-level quotas and content restrictions still apply. A July 2026 update changed quota accounting and client-ID limits; older tutorials can be misleading. [Client Credentials](https://developer.spotify.com/documentation/web-api/tutorials/client-credentials-flow), [July update](https://developer.spotify.com/blog/2026-07-23-web-api-quota-updates)

Users can also supply a playback URL without making Spotify the source of all song metadata. That preserves the approved optional provider-link role.

## When website extraction is actually relevant

Artist, promoter, venue, and ticketing pages can publish `schema.org/Event` as JSON-LD or embedded microdata. It can expose names, dates, performers, locations, and links in a machine-readable form. This is structured website extraction rather than a separately licensed public API. The standard does not license a publisher's content. [Schema.org Event](https://schema.org/Event), [Google's publisher documentation](https://developers.google.com/search/docs/appearance/structured-data/event)

In the actual initial-HTML checks, neither the [TuEntrada homepage](https://www.tuentrada.com/?lang=ar) nor the [Passline event example](https://www.passline.com/eventos/rancho-rojo-26) exposed a JSON-LD script. The latter did expose date/time and venue/address as ordinary page content. This supports HTML parsing as a technical fallback for that particular page if authorized; it does not prove that either site lacks structured data elsewhere, a private feed, or a supported integration available by agreement.

For a regional publisher without a suitable API, prefer an authorized feed/export or a source URL that the user can supply. If extraction is permitted, inspect structured data before writing brittle HTML selectors. If neither structured data nor a feed exists, DOM/HTML parsing or a browser may be technically necessary, with higher maintenance cost.

No general scrape permission or supported internal API was established for AllAccess, Ticketek Argentina, TuEntrada, Passline, Livepass, EntradaUno, or venue websites. A page's accessibility, robots rules, an internal JSON endpoint, or a browser extension does not by itself establish permission to persist and redistribute the content. Protections encountered during research were not bypassed.

## Proposed Attendance creation experience

These are research recommendations for a later design decision, not implemented behavior.

1. Search the existing Spectacles catalog first. Reusing a confirmed Event and its catalog links avoids typing and repeated provider requests.
2. Offer Event candidates from enabled, appropriately licensed providers, filtered by artist/name, approximate date, city, and country. Make source and known date/time precision visible.
3. On selection, preview the allowed artist, venue, date/time, and tour information. Reuse internal records through verified external IDs. Do not match solely by names, or use a live-album title as a tour identity.
4. Fill gaps through artist/song lookup and venue search. Allow manual completion immediately when no suitable candidate exists. Tours can stay empty, as agreed.
5. Import a setlist only from a source permitting the intended durable editable use. Normalize song candidates separately; preserve unknown titles as unresolved relational entries. A pasted source URL helps locate data but does not change its reuse rights.
6. Let the User set interest, tickets bought, and seats. Public catalogs do not establish those personal facts; partner ticket-holder APIs are not general fan-account access.
7. Keep imported details editable under the approved collaboration and catalog permissions. Do not introduce background synchronization to satisfy a provider's refresh policy: choose a suitable license/provider instead.

A provider's required attribution and retention rules may need source provenance beyond an external ID. The exact stored provenance fields and source-specific behavior should be designed after provider selection. This report does not silently alter the approved schema or enable local duplicate merging.

## Remaining work before selecting integrations

1. Compare representative Argentine and Latin American samples: major touring acts, local small venues, theatre/comedy, older concerts, multi-artist shows, and festival days. Measure Event presence and actual setlist completeness separately.
2. Test artist/work disambiguation using accented names, covers, shared titles, live recordings, and missing work links. A search hit is not a verified identity match.
3. Evaluate Geoapify versus Google and open venue data using the same regional sample. Compare missing venues, address accuracy, time-zone availability, naming changes, and permitted durable fields.
4. Obtain provider confirmation where necessary for retention, collaborative modification, mixed-source display, attribution, commercialization, and continued access after subscription cancellation. No provider was contacted in this research.
5. Verify actual access and issued quotas with deliberately approved credentials and a bounded sample. Live API behavior, registration eligibility, production approval, and matching accuracy remain untested.

The approved database design remains unchanged. This report adds the evidence needed to choose sources and identify integration constraints, especially the difference between technical availability and permission to retain editable history.
